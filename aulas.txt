## 1️⃣ Arquitetura: CPU vs GPU

| Aspecto       | CPU (Latency Oriented)                                       | GPU (Throughput Oriented)                                  |
| ------------- | ------------------------------------------------------------ | ---------------------------------------------------------- |
| Definição Conceitual | Unidade Central de Processamento → executar instruções, processar dados e gerenciar a maioria das funções de um sistema. Busca instruções na memória e as executa por meio de deus componentes internos (Unidades de controle, lógica, arimética e registradores) | Unidade de Processamento Gráfico → tipo de processador especializado em executar calculos matemáticos para renderizar imagens. Arquitetura paralela, milhares de nucles, processa grandes qtd de dados simultaneamente, sendo mais eficiente para tarefas computacionalmente intensivas. (AI e alto desempenho).
| **Objetivo**  | Minimizar latência de cada tarefa                            | Maximizar volume total de operações                        |
| **Controle**  | Complexo (previsão de desvios, pipelines curtos, forwarding) | Simples, sem previsão de desvio                            |
| **Caches**    | Grandes, otimizadas para poucos threads                      | Pequenas, otimizadas para throughput                       |
| **Execução**  | Poucos núcleos → muitas instruções complexas                 | Muitos núcleos simples → milhares de threads               |
| **Uso ideal** | Cálculos sequenciais e controle                              | Cálculos paralelos e massivos (vetores, matrizes, imagens) |

> 📊 *No slide 5 há um diagrama mostrando o paralelismo massivo da GPU: várias ALUs especialistas, pipeline profundo e controle simples para maximizar throughput.*

**Conclusão:**
A CPU é um “sprinter” (rápida em tarefas pequenas).
A GPU é um “maratonista em grupo” (lenta individualmente, mas processa milhões de operações em paralelo).

---

## 2️⃣ O Modelo de Programação CUDA

CUDA (Compute Unified Device Architecture) → Framework da NVIDIA para programação paralela em GPU.

Um programa CUDA divide-se em:

* **Host (CPU):** controla e orquestra a execução.
* **Device (GPU):** executa os kernels em paralelo.

### Estrutura de um programa CUDA

1. Alocar memória (host e device)
2. Copiar dados CPU → GPU
3. Lançar kernel (`<<<grid, block>>>`)
4. Copiar resultados GPU → CPU
5. Liberar memória

---

## 3️⃣ Gerenciamento de Memória

### Tipos de memória

* **Registers:** privados por thread.
* **Shared Memory:** visível a todas as threads do mesmo bloco.
* **Global Memory:** visível a todas as threads, mas de acesso lento.
* **Host Memory:** memória da CPU.

> ⚙️ Slide 7-8 mostra o fluxo **Host ↔ Device** e as funções principais do CUDA API.

### Funções principais

| Função                | Descrição                                           |
| --------------------- | --------------------------------------------------- |
| `cudaMalloc()`        | Aloca memória no device                             |
| `cudaFree()`          | Libera memória do device                            |
| `cudaMemcpy()`        | Copia dados entre host e device                     |
| `cudaMallocManaged()` | (Unified Memory) cria memória compartilhada CPU↔GPU |

🧩 *Unified Memory* (slide 10) → simplifica o código:

```cpp
cudaMallocManaged(&x, N*sizeof(float));
cudaFree(x);
```

O CUDA migra os dados sob demanda entre CPU e GPU, evitando cópias manuais.

---

## 4️⃣ Kernel CUDA e Execução Paralela

### Kernel

Função executada em paralelo por milhares de threads:

```cpp
__global__ void add(int n, float *x, float *y) {
    int index = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = blockDim.x * gridDim.x;
    for (int i = index; i < n; i += stride)
        y[i] = x[i] + y[i];
}
```

Chamado com:

```cpp
add<<<numBlocks, blockSize>>>(N, x, y);
```

### Indexação e Hierarquia (slides 13–15)

| Termo         | Significado           | Exemplo      |
| ------------- | --------------------- | ------------ |
| `threadIdx.x` | ID da thread no bloco | 0–255        |
| `blockIdx.x`  | ID do bloco na grid   | 0–N          |
| `blockDim.x`  | nº threads por bloco  | 256          |
| `gridDim.x`   | nº total de blocos    | depende de N |

Cada thread calcula seu **índice global**:

```cpp
int i = blockIdx.x * blockDim.x + threadIdx.x;
```

> 🔁 *Grid-Stride Loop* — padrão recomendado para lidar com vetores grandes:

```cpp
int stride = blockDim.x * gridDim.x;
for (int i = index; i < N; i += stride)
    y[i] = x[i] + y[i];
```

### Questões — Respostas concisas

- O que é uma operação stencil? Dê um exemplo prático.  
    Uma operação stencil calcula cada saída a partir de uma vizinhança fixa dos dados de entrada (p.ex. out[i,j] depende de in[i±1,j] e in[i,j±1]). Exemplo: convolução 3×3 aplicada a uma imagem (filtro de blur ou detecção de bordas).

- Explique a diferença entre uma implementação de convolução simples e uma com tiling.  
    Simples: cada thread lê diretamente da memória global todos os vizinhos necessários — muitos acessos redundantes.  
    Tiling: cada bloco carrega um subbloco (tile) + halo para shared memory; threads reutilizam dados on‑chip, reduzindo leituras globais e aumentando throughput.

- Qual o papel da memória compartilhada em um stencil?  
    Serve como cache on‑chip por bloco para armazenar tiles e halos, permitindo reuso de dados entre threads do mesmo bloco com baixa latência e evitando contenção na memória global.

- O que é o halo e por que ele é necessário?  
    Halo é a margem de vizinhos extra carregada junto ao tile para que threads na borda do tile tenham acesso às entradas necessárias ao stencil. Sem halo, cálculos de borda exigiriam leituras adicionais da memória global ou resultados incorretos.

- Como o tamanho do bloco (tile) influencia o throughput em GPU?  
    Tile pequeno → subocupação e underutilização; tile grande → mais shared memory por bloco e possivelmente menor ocupação dos SMs. Existe um ponto ótimo (trade‑off entre reutilização de dados e ocupação) que maximiza throughput.

- O que são warps e por que é importante usar múltiplos de 32 threads?  
    Warp = grupo de 32 threads que executam a mesma instrução (SIMT). Usar blocos com múltiplos de 32 evita threads ociosas dentro de warps, reduz divergência interna e melhora eficiência/ocupação.

# 🧠 **AULA 14 — Data Race, Atomics e Throughput em GPU**

---

## 1️⃣ **Recapitulando: CPU x GPU**

* *CPU → Speed / latência*: poucas threads, alto desempenho individual.
* *GPU → Throughput / largura de banda*: milhares de threads simultâneas.

O slide 4 dos materiais mostra bem a analogia:

> **Speed = moto (velocidade individual)** vs **Throughput = ônibus (muitos passageiros por viagem)** .

---

## 2️⃣ **O Problema das Data Races**

Uma **condição de corrida** ocorre quando **duas ou mais threads acessam a mesma variável compartilhada** simultaneamente e **pelo menos uma delas escreve** sobre ela.

Em CUDA, isso é especialmente perigoso, pois:

* Milhares de threads executam em paralelo.
* As operações em memória não são atômicas por padrão.
* Uma escrita simultânea pode corromper o resultado.

### Exemplo: incremento concorrente

```cpp
__global__ void histograma_ingenuo(int *dados, int *hist, int N) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < N) hist[dados[i]]++;   // condição de corrida!
}
```

> Cada thread lê → soma → escreve.
> Se duas threads fizerem isso ao mesmo tempo no mesmo índice, uma escrita é perdida.

---

## 3️⃣ **Operações Atômicas**

Uma **operação atômica** garante que o acesso a um endereço de memória seja **exclusivo e indivisível**.

```cpp
atomicAdd(&hist[dados[i]], 1);
```

✅ Corrige o problema.
❌ Mas força **serialização** — todas as threads que disputam o mesmo índice esperam em fila.

> Segundo o slide 12, todas as operações atômicas na DRAM são **executadas de forma serializada**, com latência de leitura + escrita para cada operação .

---

## 4️⃣ **Custos e Localização das Atomics**

| Local da operação | Latência relativa | Escopo                     | Observações                                 |
| ----------------- | ----------------- | -------------------------- | ------------------------------------------- |
| **DRAM (global)** | ~10× maior        | Toda a GPU                 | Serialização total                          |
| **Cache L2**      | ~1/10 da DRAM     | Compartilhada entre blocos | Menor custo, mas ainda limitada             |
| **Shared Memory** | Muito baixa       | Dentro do bloco            | Ideal para reduções locais; impacto mínimo  |

---

## 5️⃣ **Reestruturando o Algoritmo: Evitar Atomics**

### Estratégia 1 — **Divisão por Blocos (Local Histogram)**

* Cada bloco cria seu **histograma local** em *shared memory*.
* Threads incrementam livremente, sem atomics globais.
* No final, o bloco grava seu resultado parcial na memória global.
* Uma etapa final (na CPU ou em outro kernel) faz a fusão dos parciais.

```cpp
__global__ void histograma_compartilhado(const int *dados, int *hist_blocos, int N, int numChunks) {
    extern __shared__ int hist_local[];
    int tid = blockIdx.x * blockDim.x + threadIdx.x;

    for (int i = threadIdx.x; i < numChunks; i += blockDim.x)
        hist_local[i] = 0;
    __syncthreads();

    if (tid < N) {
        int chunk = dados[tid];
        hist_local[chunk]++;
    }
    __syncthreads();

    for (int i = threadIdx.x; i < numChunks; i += blockDim.x)
        hist_blocos[blockIdx.x * numChunks + i] = hist_local[i];
}
```

Essa versão usa apenas memória compartilhada → sem contenção global.

### Estratégia 2 — **Redução por Bloco + Fusão**

* Cada bloco produz um vetor local.
* A CPU ou um segundo kernel faz a soma final (reduction entre blocos).
* Sem atomics entre threads de blocos diferentes.

---

## 6️⃣ **Throughput — Medindo Desempenho**

O **throughput** mede quantas operações a GPU executa por segundo.

[
\text{Throughput (M ops/s)} = \frac{N}{t_s × 10^6}
]
onde (t_s = t_{ms}/1000).

Onde: 
- N = Número total de operações executadas (elementos processados)
- Tempo total do kernel em segundos


Usando `cudaEventRecord` → `cudaEventElapsedTime()`.
O slide 4 traz a analogia de speed vs throughput → motocicleta vs ônibus.

> GPUs têm throughput enorme, mas latência alta por thread; sincronizações e atomics reduzem fortemente essa taxa.

---

## 7️⃣ **Comparativo das Três Abordagens de Histograma**

| Versão        | Correta? | Custo               | Throughput esperado  | Observação                           |
| ------------- | -------- | ------------------- | -------------------- | ------------------------------------ |
| Ingênua       | ❌ (Não)  | —                   | Alta (mas incorreta) | Data race corrompe resultado         |
| Atômica       | ✅        | Alto (c/ contenção) | Muito baixo          | Cada thread espera na mesma variável |
| Compartilhada | ✅        | Baixo               | Muito alto           | Acesso independente por bloco        |



---

## 8️⃣ **Conclusão**

* Atomics → garantem correção mas destroem throughput.
* Sincronizações custam caro em GPU porque são amplificadas por milhares de threads.
* Otimize para **evitar acessos compartilhados entre threads**.
* Use **memória compartilhada por bloco** para reduções locais.
* **Throughput alto** depende de acessos independentes.

## 💬 Questões possíveis de prova (dissertativas)

1. Condição de corrida (data race) em GPU  
    Uma condição de corrida ocorre quando duas ou mais threads acessam a mesma localização de memória simultaneamente e ao menos uma escreve, sem sincronização. Em GPU isso é mais crítico porque há milhares de threads executando em paralelo com acesso direto à memória global e sem coerência de cache por thread: conflitos são muito mais frequentes e efeitos não determinísticos aparecem mais facilmente do que em programas CPU com poucas threads.

2. Comparação: `atomicAdd()` (GPU) vs `#pragma omp atomic` (CPU)  
    - Em resumo: ambos garantem correção, mas o custo relativo depende do número de threads, da hierarquia de memória e do nível de contenção (GPU sofre mais em escala massiva).

3. Por que atomics na memória global causam baixa performance?  
    Porque atomics globais geram serialização e latência alta: cada operação deve ser coordenada no subsistema de memória (DRAM/L2), criando filas de espera, stalls nas threads e perda de ocupação dos SMs. Em muitos conflitos, o throughput cai drasticamente porque as operações deixam de ser paralelas e passam a se comportar sequencialmente.

4. Como a memória compartilhada ajuda a mitigar contenção?  
    A memória compartilhada (shared memory) é on‑chip, com latência muito baixa e escopo por bloco. Estratégia comum: cada bloco acumula localmente (sem atomics globais), usando arrays/atomics locais ou redução por threads, e só depois escreve um resultado parcial na memória global. Isso reduz drasticamente o número de operações atômicas globais e melhora reutilização de dados.

5. Conceito de throughput e como calculá‑lo  
    Throughput = quantidade de trabalho / tempo (ex.: operações por segundo). Medida prática: throughput (Mops/s) = N / (t_ms / 1000) / 1e6 = N / (t_s) / 1e6, onde N = número de operações e t_ms = tempo em milissegundos. Em GPU costuma‑se medir tempo com `cudaEventRecord()` / `cudaEventElapsedTime()` e calcular operações efetivas por segundo para comparar abordagens.
    - `atomicAdd()` é uma primitiva de hardware/driver que garante atomicidade no device; em alta contenção ela provoca serialização ao nível da memória (especialmente DRAM), degradando throughput.  
    - `#pragma omp atomic` implementa atomicidade no host via instruções atômicas ou sincronização do compilador/OS; com menos threads e caches coerentes, a penalidade costuma ser menor, mas ainda causa ordenação/espera.

# 🧠 **AULA 15 — Programação Paralela em GPU: Stencil, Tiling e Agendamento de Threads**

---

## 1️⃣ **O que é uma operação Stencil**

Um **Stencil Operation** é um padrão computacional no qual **cada elemento de saída depende da vizinhança de elementos de entrada**.
Exemplo 2D comum:
[
out[i,j] = f(in[i−1,j], in[i,j−1], in[i,j], in[i+1,j], in[i,j+1])
]

👉 Usado em:

* Convoluções (filtros de imagem)
* Difusão de calor
* Simulações físicas (métodos numéricos de diferenças finitas)
* Processamento de sinais/matrizes

---

## 2️⃣ **Problema em GPU: Reuso e Overhead de Memória Global**

Na GPU, cada thread calcula um pixel/ponto.
➡️ Threads vizinhas **reacessam os mesmos dados da memória global**, o que gera **muitos acessos redundantes** e **baixa eficiência**.

### 💡 Solução: **Tiling com Shared Memory**

Cada bloco de threads carrega:

* Um **tile (bloco)** da matriz principal.
* Mais uma **margem (halo)** com os vizinhos necessários para computar os pixels na borda.

Assim, o acesso à memória global é reduzido e o **reuso** de dados é maximizado.

---

## 3️⃣ **Exemplo — Convolução 3×3**

### Código base (sem otimização)

```cpp
__global__ void conv2D(float *input, float *output, float *mask,
                       int width, int height) {
    int i = blockIdx.y * blockDim.y + threadIdx.y;
    int j = blockIdx.x * blockDim.x + threadIdx.x;

    float acc = 0.0f;

    for (int y = -1; y <= 1; y++) {
        for (int x = -1; x <= 1; x++) {
            int r = i + y, c = j + x;
            if (r >= 0 && r < height && c >= 0 && c < width)
                acc += input[r * width + c] * mask[(y+1)*3 + (x+1)];
        }
    }
    output[i * width + j] = acc;
}
```

➡️ Correta, mas lenta: cada pixel lido várias vezes por threads diferentes.

---

## 4️⃣ **Tiling com Shared Memory e Halo**

### Ideia geral

* **Tile:** submatriz local do bloco.
* **Halo:** margem que cobre vizinhos do tile.
* **`__syncthreads()`**: sincroniza o carregamento antes do cálculo.

### Código otimizado

```cpp
#define TILE_SIZE 16
#define MASK_RADIUS 1
#define MASK_SIZE 3

__global__ void conv2D_tiled(float *input, float *output, float *mask,
                             int width, int height) {
    int tx = threadIdx.x, ty = threadIdx.y;
    int j = blockIdx.x * TILE_SIZE + tx;
    int i = blockIdx.y * TILE_SIZE + ty;

    __shared__ float tile[TILE_SIZE + 2 * MASK_RADIUS][TILE_SIZE + 2 * MASK_RADIUS];

    int inputRow = i - MASK_RADIUS;
    int inputCol = j - MASK_RADIUS;

    if (inputRow >= 0 && inputRow < height && inputCol >= 0 && inputCol < width)
        tile[ty][tx] = input[inputRow * width + inputCol];
    else
        tile[ty][tx] = 0.0f;

    __syncthreads();

    if (tx >= MASK_RADIUS && tx < TILE_SIZE + MASK_RADIUS &&
        ty >= MASK_RADIUS && ty < TILE_SIZE + MASK_RADIUS &&
        i < height && j < width) {
        float acc = 0.0f;
        for (int y = -MASK_RADIUS; y <= MASK_RADIUS; y++)
            for (int x = -MASK_RADIUS; x <= MASK_RADIUS; x++)
                acc += tile[ty + y][tx + x] * mask[(y + 1)*3 + (x + 1)];

        output[i * width + j] = acc;
    }
}
```

✅ **Benefícios:**

* Reduz acessos à memória global.
* Reuso de dados via *shared memory*.
* Melhora significativa no throughput.

---

## 5️⃣ **Agendamento de Threads e Warps**

A GPU organiza a execução hierarquicamente:

* **Warp:** grupo de 32 threads que executam em modo **SIMT** (*Single Instruction, Multiple Thread*).
* **SM (Streaming Multiprocessor):** unidade que executa vários warps em paralelo.
* **Agendador:** alterna warps prontos → esconde latência de memória.

### ⚙️ Boas práticas

| Boas práticas                                   | Explicação                                 |
| ----------------------------------------------- | ------------------------------------------ |
| **Usar blocos com múltiplos de 32 threads**     | Alinhamento com tamanho de warp            |
| **Evitar divergência de fluxo**                 | `if` dentro do warp reduz eficiência       |
| **Maximizar ocupação**                          | Mais blocos ativos → mais warps por SM     |
| **Usar `cudaOccupancyMaxPotentialBlockSize()`** | Função que sugere o tamanho ótimo de bloco |

---

## 6️⃣ **Exemplo prático — Heat Stencil 2D com Tiling e Análise**

O kernel `heatStencil2D` aplica um *stencil* de difusão de calor, simulando 100 iterações locais sobre uma matriz 8192×8192.

### Principais otimizações:

* Memória unificada (`cudaMallocManaged`).
* Memória compartilhada dinâmica (`extern __shared__`).
* Blocos configurados conforme **ocupação ótima teórica**.
* Medição de tempo via `cudaEventRecord`.
* Avaliação do desempenho em **Mpx/s (milhões de pixels por segundo)**.

### Comando SLURM

```bash
#!/bin/bash

#SBATCH --partition=gpu
#SBATCH --gres=gpu:1
#SBATCH --time=00:10:00
#SBATCH --mem=4G

```

## 7️⃣ **Análise de Desempenho (Tile Size vs Throughput)**

| Tile  | Threads/bloco | Mpx/s  | Comentário                          |
| ----- | ------------- | ------ | ----------------------------------- |
| 8×8   | Baixo         | Menor  | Subocupação                         |
| 12×12 | Médio         | ↑      | Melhora                             |
| 16×16 | Médio-alto    | ↑↑     | Melhor equilíbrio                   |
| 25×25 | Ideal teórico | Máximo | Ponto ótimo                         |
| 32×32 | Muito alto    | ↓      | Alta shared memory → menor ocupação |

📊 **Conclusões:**

* Blocos muito pequenos → *baixa ocupação* (GPU subutilizada).
* Blocos muito grandes → *alta shared memory por bloco* → menos blocos ativos por SM.
* Melhor desempenho = **ponto de equilíbrio com Mpx/s máximo**.

## 💬 **Questões dissertativas que podem cair**

## Questões — Respostas concisas

1. O que é uma operação *stencil*? Dê um exemplo prático.  
    Uma operação stencil calcula cada saída a partir de uma vizinhança fixa dos dados de entrada. Ex.: convolução 3×3 aplicada a uma imagem (blur ou detecção de bordas), onde out[i,j] depende de in[i±1,j] e in[i,j±1].

2. Explique a diferença entre uma implementação de convolução simples e uma com tiling.  
    Simples: cada thread lê diretamente da memória global todos os vizinhos necessários — muitos acessos redundantes.  
    Tiling: cada bloco carrega um tile + halo para shared memory; threads reutilizam dados on‑chip, reduzindo leituras globais e aumentando throughput.

3. Qual o papel da memória compartilhada em um stencil?  
    Age como cache on‑chip por bloco: armazena tiles/halos, permite reuso entre threads do mesmo bloco com baixa latência e reduz contenção na memória global.

4. O que é o halo e por que ele é necessário?  
    Halo = margem de vizinhos extra carregada junto ao tile para que threads na borda tenham acesso às entradas necessárias ao stencil. Sem halo, bordas exigiriam leituras adicionais da memória global ou resultados incorretos.

5. Como o tamanho do bloco (tile) influencia o throughput em GPU?  
    Tile pequeno → subocupação (GPU subutilizada).  
    Tile muito grande → maior uso de shared memory por bloco → menos blocos ativos por SM.  
    Existe um ponto ótimo (trade‑off entre reutilização de dados e ocupação) que maximiza o throughput.

6. O que são warps e por que é importante usar múltiplos de 32 threads?  
    Warp = grupo de 32 threads que executam a mesma instrução (SIMT). Usar blocos com múltiplos de 32 evita threads ociosas dentro do warp, reduz divergência interna e melhora eficiência/ocupação.

# 🧠 AULA 16 — Redução e Scan com CUDA (Reductions & Prefix-sum)



## 1️⃣ Conceito: O que é Redução?

Redução: transformar um vetor de N elementos em um único valor aplicando uma operação associativa (soma, max, min, prod…).

Sequencial: `sum = 0; for i sum += a[i];`

Paralela em GPU: usar árvore binária em etapas — metade das operações a cada iteração — até sobrar 1 valor.

### Exemplo conceitual (N=8)

1. pares: (x0+x1),(x2+x3),(x4+x5),(x6+x7) → 4 resultados
2. pares: (r0+r1),(r2+r3) → 2 resultados
3. final: r0+r1 → 1 resultado

---

## 2️⃣ Implementação base (por bloco) — principais pontos

* **Cada bloco** reduz uma parte do vetor (ex.: 2×blockDim.x elementos → cada thread carrega 2 valores).
* **shared memory** armazena somas parciais (`extern __shared__ float partial[];`).
* Loop de redução com `stride` decrescendo: **usar `if (t < stride)`** (versão contígua) — evita warp divergence e melhora localidade:

```cpp
for (unsigned int stride = blockDim.x; stride > 0; stride >>= 1) {
    __syncthreads();
    if (t < stride)
        partial[t] += partial[t + stride];
}
```

* Ao final, `partial[0]` tem o resultado parcial do bloco; escreve em `output[blockIdx.x]`.
* Para obter soma total: relançar o kernel sobre `output` recursivamente até restar 1 elemento (ou copiar para host e finalizar).

**Observações práticas:**

* Carregar 2 elementos por thread melhora largura de banda e reduz número de passos.
* Use `__syncthreads()` entre passos.
* Evitar condicionais que saltem threads nos warps (ex.: `t % stride == 0`) — causa execução parcial de warps e perda de throughput.

---

## 3️⃣ Problemas comuns & por que `if (t < stride)` é melhor

* *Versão espaçada* `if (t % stride == 0)` ativa threads espalhadas → warps executam parcialmente → baixa eficiência.
* *Versão contígua* `if (t < stride)` ativa prefixos consecutivos → warps executam uniformemente até as etapas finais (quando número de threads < 32).
* Localidade de memória: acessos são contíguos → melhor uso de caches/shared memory.

---

## 4️⃣ Redução multi-bloco (padrão de produção)

Padrão:

1. Kernel A: cada bloco reduz seu segmento → escreve `partial[blockIdx.x]`.
2. Caso `numBlocks > 1`, relançar Kernel A sobre o vetor `partial` até sobrar 1 (loop recursivo) ou:

   * copiar `partial` para host e finalizar (bom para `numBlocks` pequeno),
   * ou executar um kernel final com 1 bloco que reúne tudo.

Dicas:

* Para grandes N, escolha `threadsPerBlock` = múltiplo de 32 (warps).
* Especificar `sharedMem` ao lançar (`<<<numBlocks, threads, sharedMemBytes>>>`).

---

## 5️⃣ Scan (Prefix Sum) — por que é diferente

* Redução retorna 1 valor; **scan** retorna N valores: `out[i] = sum_{k=0}^{i-1} in[k]` (scan exclusivo).
* Scan é usado em **compactação, construção de índices, stream compaction, radix sort, etc.**

### Algoritmo eficiente: Blelloch (Up-sweep + Down-sweep)

**Fase 1 — Up-sweep (reduce):** constrói somas parciais em uma árvore (como redução).

**Fase 2 — Down-sweep (distribute):** começa com `last = 0` e propaga prefixos, calculando os valores finais sem repetir somas.

Implementação típica (por bloco, carregando 2 elementos por thread):

* `tamanho_bloco = 2 * blockDim.x`
* Carrega dois elementos por thread para `shared`:

  ```cpp
  aux[tid] = in[i];
  aux[tid + blockDim.x] = in[i + blockDim.x];
  ```
* Up-sweep:

  ```cpp
  for (int stride=1; stride < tamanho_bloco; stride *= 2) {
      int idx = (tid+1)*stride*2 - 1;
      if (idx < tamanho_bloco) aux[idx] += aux[idx - stride];
      __syncthreads();
  }
  ```
* Zera o último elemento (`aux[tamanho_bloco-1]=0`) (para scan exclusivo) e faz down-sweep:

  ```cpp
  for (int stride = tamanho_bloco/2; stride >= 1; stride /= 2) {
      int idx = (tid+1)*stride*2 - 1;
      if (idx < tamanho_bloco) {
          int t = aux[idx - stride];
          aux[idx - stride] = aux[idx];
          aux[idx] += t;
      }
      __syncthreads();
  }
  ```
* Escrever `aux` de volta em `saida`.

**Nota:** A versão por bloco produz *scan* local; para vetor maior que bloco, é necessário:

1. calcular scan em cada bloco (produz scan local e soma parcial do bloco),
2. fazer scan das somas parciais (em host ou kernel),
3. adicionar deslocamento (offset) a cada bloco.

---

## 6️⃣ Otimizações adicionais (práticas de produção)

* **Shuffle intrinsics** (`__shfl_xor_sync`, etc.): reduções por warp sem shared memory e sem `__syncthreads()` são muito rápidas (útil quando reduzir dentro do warp).
* **Unrolling** dos últimos passos para reduzir overhead de sincronização.
* **Carregar 2 (ou 4) elementos por thread** para melhorar coalescing e reduzir passos.
* **Evitar bank conflicts** em shared memory: endereçamento adequado (padding se necessário).
* **Usar `volatile`** em versões antigas para evitar caches quando necessário (menos comum hoje).
* **Medição**: use `cudaEventRecord` para medir tempo de kernels; use Nsight para métricas de occupancy/memory stalls.

---

## 7️⃣ Código(s) essenciais (resumido)

### Redução contígua (per-block, 2 elementos por thread)

```cpp
__global__ void reduceShared(float *input, float *output, int N) {
    extern __shared__ float partial[];
    unsigned int t = threadIdx.x;
    unsigned int start = 2 * blockIdx.x * blockDim.x;

    // load up to 2 elements per thread
    partial[t] = (start + t < N) ? input[start + t] : 0.0f;
    partial[blockDim.x + t] = (start + blockDim.x + t < N) ? input[start + blockDim.x + t] : 0.0f;
    __syncthreads();

    for (unsigned int stride = blockDim.x; stride > 0; stride >>= 1) {
        __syncthreads();
        if (t < stride)
            partial[t] += partial[t + stride];
    }
    if (t == 0)
        output[blockIdx.x] = partial[0];
}
```

## 8️⃣ Questões dissertativas possíveis (prova)

## Respostas rápidas 

1) Por que `if (t % stride == 0)` é ruim para GPU  
- Ativa threads espaçadas (não prefixo), causando execução parcial de warps → warp divergence e underutilização.  
- Acessos aos elementos parceiros ficam não contíguos → pior coalescing e localidade.  
- Mais branchs e sincronizações desnecessárias; a versão contígua `if (t < stride)` preserva prefixos ativos, reduz divergência e melhora throughput.

2) Algoritmo Blelloch (Up‑sweep / Down‑sweep) e work‑efficiency  
- Up‑sweep: em passos log2(N) soma pares em níveis (constrói soma parcial em árvore).  
- Set last = 0 (para scan exclusivo).  
- Down‑sweep: percorre a árvore invertida, trocando e propagando prefixos para produzir os valores de scan.  
- Complexidade: profundidade O(log N), trabalho total Θ(N) — work‑efficient porque faz ordem linear de operações, sem multiplicar o custo assintoticamente em relação ao sequencial.

3) Scan para vetores maiores que um bloco (offsets por bloco)  
- Passo A: executar scan por bloco (cada bloco gera scan local + soma total do bloco).  
- Passo B: reunir as somas totais dos blocos e executar um scan sobre esse vetor de somas (pode ser no host ou em outro kernel).  
- Passo C: aplicar um kernel que adiciona o offset (scan das somas parciais) a todos os elementos de cada bloco — assim cada bloco recebe o deslocamento correto e o scan global fica completo.

4) Otimizações práticas para redução em vetor gigante  
- Carregar 2 (ou 4) elementos por thread para melhorar bandwidth e coalescing.  
- Reduzir em shared memory por bloco com padrão contíguo (`if (t < stride)`).  
- Usar shuffle intrinsics dentro do warp para evitar shared memory/sincronização nos passos finais.  
- Unroll das últimas iterações para reduzir overhead.  
- Evitar bank conflicts (padding se necessário).  
- Ajustar threadsPerBlock para maximizar occupancy; medir com `cudaOccupancyMaxPotentialBlockSize`.  
- Minimizar comunicação global: escrever só um parcial por bloco e combinar recursivamente (ou copiar pequenas parciais ao host).  
- Medir com `cudaEvent` e perfilar (Nsight) para guiar otimizações.

5) Uso e vantagem das intrinsics de shuffle (`__shfl_*`)  
- Permitem trocar valores entre lanes de um warp sem usar shared memory nem `__syncthreads()`.  
- Reduções por warp com `__shfl_xor_sync(mask, val, offset)` são muito rápidas (latência bem menor que acessos a shared).  
- Limitação: só operam dentro do warp (32 lanes); para reduzir além do warp combina-se shuffle + escrita de resultados por warp em shared memory e redução final entre warps.  
- Exemplo compacto:  
    - val ^= __shfl_xor_sync(0xffffffff, val, 1); // padrão de troca XOR para reduzir dentro do warp (esquema ilustrativo)

# 🧠 AULA 17 — Matrizes Esparsas (CSR) e Computação Assíncrona (Streams)

---

## 1️⃣ Matrizes esparsas — conceitos e por que importar

* Matriz esparsa: a maioria dos elementos é zero.
* Armazenar zeros é desperdício de memória e causa overhead de processamento.
* Formatos populares: **CSR (Compressed Sparse Row)**, COO, ELL, CSC.
* **CSR** é o mais usado para SpMV em HPC por ser compacto e favorecer leitura por linha (row-major).

### Estruturas CSR

* **values[]** — valores não-nulos, armazenados linha por linha.
* **col_idx[]** — índice da coluna correspondente para cada value.
* **row_ptr[]** — tamanho = (#linhas + 1); row_ptr[i] é o índice em values onde começa a linha i; row_ptr[i+1] - row_ptr[i] é o número de nnz na linha i.

Ex.: para linha i, percorre valores entre `row_ptr[i]` e `row_ptr[i+1]-1`.

---

## 2️⃣ SpMV (A * x) em CSR — abordagem direta (cada thread por linha)

Código essencial (já presente no seu material — explicado aqui com ênfase):

```cpp
__global__ void multiplicar_csr_kernel(
    int num_linhas,
    const int *row_ptr,
    const int *col_idx,
    const float *val,
    const float *x,
    float *y)
{
    int row = blockIdx.x * blockDim.x + threadIdx.x;
    if (row < num_linhas) {
        float sum = 0.0f;
        int start = row_ptr[row];
        int end   = row_ptr[row + 1];
        for (int i = start; i < end; ++i) {
            int c = col_idx[i];
            sum += val[i] * x[c];
        }
        y[row] = sum;
    }
}
```

### Vantagens

* Simples, cada thread processa uma linha independente → fácil paralelizar.

### Problemas / gargalos

* **Load imbalance**: linhas têm nnz muito diferentes — algumas threads fazem pouco trabalho, outras muito (subutilização).
* **Acesso a x[] não coalescente**: índices de coluna aleatórios causam leituras com baixa localidade/cache misses.
* **Divergência** na latência entre threads ao percorrer linhas com diferentes comprimentos.
* **Underutilization** quando #linhas < #threads desejadas (p.ex. linhas poucas, muitas colunas).

---

## 3️⃣ Técnicas de otimização para SpMV em GPU

1. **Balanceamento de carga**

   * *Warp-based*: atribuir uma linha por *warp* quando a linha tem muitos nnz (cada warp procesa a linha em paralelo).
   * *Dynamic parallelism / work queuing*: dividir linhas maiores entre várias threads/warps.
   * *Row reordering*: ordenar linhas por nnz para agrupar linhas com similar carga (reduz variação).

2. **Formato ELL/Hybrid (ELL + CSR)**

   * ELL: bom quando nnz por linha é uniforme — armazena colunas até um K fixo por linha; coalescing melhor.
   * Hybrid (ELL + CSR): ELL para linhas com ≤K elementos, CSR para as restantes.

3. **Uso de memória**

   * Prefetch e cache (se disponível): prefetch x[] para shared memory quando a mesma região de x é muito reutilizada.
   * Evitar escrita dispersa; garantir coalescing na leitura de values[] e col_idx[] (armazenamento contíguo).

4. **Segmented reduction**

   * Quando várias threads (ou warps) participam da soma de uma mesma linha, usar redução por warp + atomic em shared/global com menos contention.

5. **Uso de atomics (com cautela)**

   * Em esquemas onde múltiplos warps escrevem no mesmo y[row], pode ser necessário `atomicAdd`. Mas atomics globais podem ser caros — prefira reduzir localmente e só depois usar atomics ou ter cada warp escrever em posição exclusiva.

6. **Bibliotecas otimizadas**

   * Use cuSPARSE, cuSPARSE SpMV routines, que aplicam otimizações específicas de hardware.

---

## 4️⃣ Computação assíncrona com streams — conceito e padrões

### O que é uma stream?

* Fila de comandos assíncronos (memcpy async, kernels, etc.).
* Comandos dentro de uma mesma stream são sequenciais; comandos em streams diferentes podem ocorrer concorrente, dependendo do hardware (copy engines, concorrência de kernels).

### Objetivo

* **Sobrepor**: transferências H2D/D2H com execução de kernel para reduzir tempo total (overlap).
* Permitir que CPU continue a preparar outros lotes sem ficar bloqueada.

### Padrões de uso

* **Pipeline por blocos/chunks**: dividir dados grandes em N chunks; para cada chunk:

  * `cudaMemcpyAsync(d_chunk, h_chunk, ..., stream[i])`
  * `kernel<<<blocks, threads, 0, stream[i]>>>(d_chunk, ...)`
  * `cudaMemcpyAsync(h_chunk_out, d_chunk, ..., stream[i])`
* Use múltiplas streams para criar um pipeline: enquanto stream0 executa kernel, stream1 pode copiar dados do host para device, etc.

### Atenção ao hardware

* GPUs têm um número limitado de *copy engines* (motor de cópia). Em alguns GPUs só 1 motor, então nem todas as cópias com streams diferentes podem ocorrer 100% concorrentes.
* Concorrência de kernels: depende do dispositivo — alguns suportam múltiplos kernels concorrentes.

---

## 5️⃣ Exemplo comparativo: síncrono vs assíncrono (seu código)

* Síncrono: para cada chunk → H2D → kernel → D2H (sequencial).
* Assíncrono: lança `cudaMemcpyAsync` + kernel no mesmo stream para cada chunk; usar várias streams para paralelizar cópias e execuções; ao final `cudaStreamSynchronize` em cada stream.

**Ganho esperado**: speedup > 1 (depende de tamanho dos chunks, latência PCIe, número de streams, presença de copy engines). Seu exemplo mostra medição com `cudaEventRecord()` para comparar os tempos.

---

## 6️⃣ Recomendações práticas para usar streams bem

* **Escolha do chunk size** — tradeoff:

  * chunks grandes → melhor eficiência do kernel (mais trabalho por chamada), mas menos oportunidade de overlap.
  * chunks muito pequenos → overhead de enfileiramento e menor eficiência do kernel.
  * teste empiricamente (Média de 4–16 streams é comum, mas depende do trabalho e do GPU).

* **Pinned host memory** (`cudaHostAlloc` / `cudaMallocHost`) para permitir DMA e transferências assíncronas com maior throughput.

* **Reutilizar buffers** na device para evitar overhead de `cudaMalloc` repetido.

* **Streams e dependências**:

  * Use `cudaEventRecord` + `cudaStreamWaitEvent` quando precisar de sincronização entre streams.
  * Cuidado: operações em stream0 (default) e em outras streams podem interagir com recursos comuns (L2, memory bus).

* **Profiling**:

  * Use Nsight Systems para ver timeline e identificar oportunidades reais de overlap e gargalos (copy engine ocupado, kernel saturado, etc).
  * Meça com `cudaEventRecord` para comparar síncrono vs assíncrono.

---

## 7️⃣ Padrões de otimização combinados (SpMV + streams)

* **Chunk the matrix rows**: dividir o conjunto de linhas em blocos que caibam na memória do device e processá-los por streams — permite pipeline H2D / Kernel / D2H.
* **Overlap transfers das estruturas CSR** (values, col_idx, row_ptr) e x[] — mas note: x[] é frequentemente necessário em full para cada chunk; prefira manter x[] na GPU quando possível (evita cópias repetidas).
* **Mantendo x[] na GPU**: se x é reutilizado, copie x uma vez e mantenha; então só envie blocos de values/col_idx/row_ptr ou apenas offsets para processamento.
* **Prefetch e memory advice com Unified Memory** (`cudaMemPrefetchAsync`) em arquiteturas que suportam — às vezes mais simples do que gerenciar cópias em streams.

---

## 8️⃣ Medição e profiling (o que olhar)

* **Throughput / bandwidth**: bytes por segundo lidos da global memory; se estiver no teto do DRAM, otimizações precisam reduzir tráfego.
* **Occupancy**: warps ativas por SM — se baixo, ajustar threads por bloco.
* **Warp execution efficiency**: se baixa → divergência.
* **Copy engine utilization**: para streams, verificar se as cópias estão sendo enfileiradas e realizados em paralelo.
* **Roofline**: identificar se código é memory-bound ou compute-bound.

Use `nsys`, `nvprof` (deprecated) ou `nv-nsight-cucli`/Nsight Compute.

## 11️⃣ Erros comuns / pegadinhas para prova

1) Formato CSR — por que eficiente para SpMV  
- Estrutura: values[] (valores não‑nulos), col_idx[] (índices de coluna), row_ptr[] (ponteiros de início das linhas, tamanho = nrows+1).  L2 bandwidth.
- Vantagens: armazena só os nnz → menor uso de memória; iteração por linha é contígua em values/col_idx → bom padrão de acesso sequencial; acesso por linha combina bem com SpMV (cada thread/warp percorre row_ptr[i]..row_ptr[i+1]-1), reduz overhead de índices.

2) Problemas típicos de desempenho com 1 thread por linha e como mitigar  
- Problemas:
    - Load imbalance (linhas com nnz muito desiguais).  
    - Acessos a x[] não coalescentes (col_idx aleatório) → muitos misses.  
    - Divergência de tempo entre threads → subutilização dos SMs.  
    - Underutilização quando #linhas pequeno.  
- Mitigações:
    - Warp‑based ou multi‑thread por linha para linhas longas (dividir trabalho).  
    - Reordenar linhas por carga ou usar formatos híbridos (ELL+CSR) quando nnz/linha é uniforme.  
    - Prefetch / copiar blocos de x[] para shared memory quando houver reutilização local.  
    - Usar redução segmentada por warp (evitar atomics globais) e bibliotecas otimizadas (cuSPARSE).

3) O que é uma stream CUDA e exemplo de pipeline para overlap  
- Stream = fila de operações assíncronas (memcpy async, lançamentos de kernel); operações na mesma stream são sequenciais; entre streams podem ocorrer em paralelo dependendo do hardware.  
- Para sobrepor cópia e execução: usar cudaMemcpyAsync + kernel no mesmo stream e múltiplas streams em pipeline. Exemplo (pseudo):

    1. para cada chunk i:
         - cudaMemcpyAsync(h->d, chunk[i], stream[i%S])
         - kernel<<<...,...,0,stream[i%S]>>>(d_chunk...)
         - cudaMemcpyAsync(d->h, out[i], stream[i%S])
    2. usar memoria host pinada e depois sincronizar streams.  
- Resultado: enquanto stream A executa kernel, stream B pode fazer H2D do próximo chunk (overlap H2D ⇄ kernel).

4) Quando manter x[] na GPU em vez de copiá‑lo por chunk  
- Manter x[] no device é melhor quando:
    - x[] é reutilizado por muitos chunks/kernels (iterativos ou múltiplos SpMV).  
    - x[] cabe na memória do dispositivo.  
    - PCIe/transferências se tornam gargalo ou custo de cópia supera ganho do chunking.  
- Regra prática: se x[] for lido frequentemente e não mudar entre chamadas, copie uma vez e deixe na GPU.

5) Limitações ao usar muitas streams — quais recursos viram gargalo  
- Possíveis gargalos:
    - Número de copy engines do dispositivo (nem todas as cópias podem ser paralelas).  
    - Largura de banda PCIe (H2D/D2H) — saturação impede overlap efetivo.  
    - Banda de memória do device (L2/DRAM) — múltiplos kernels competem pelo mesmo bandwidth.  
    - Scheduler e limites de concorrência de kernels (hardware limitado a certo nº de kernels concorrentes).  
    - Overhead da criação/gerenciamento de streams e escassez de memória pinada.  
- Consequência: além de mais streams não garantirem ganho, podem aumentar contenção (DRAM/L2/PCIe) e overhead: medir e escolher número/size de chunks adequados (4–16 é ponto de partida típico).os heterogêneos.
* Usar atomics no y[] sem justificar — atomics em DRAM são caros; prefira design que leve cada thread a escrever uma posição exclusiva.

## 12️⃣ Ficha de bolso (resumo rápido para prova)

* **CSR:** `values[]`, `col_idx[]`, `row_ptr[]` (size = nrows+1). Iterar linha i entre `row_ptr[i]..row_ptr[i+1]-1`.
* **SpMV (simples):** 1 thread por linha — simples, porém pode sofrer *load imbalance* e acessos não-coalescentes a x[].
* **Otimizações:** warp-based, ELL/hybrid, prefetch de x, manter x na GPU, reduzir atomics.
* **Streams:** `cudaMemcpyAsync`, `kernel<<<...,...,0,stream>>>`, `cudaMemcpyAsync` — permite overlap H2D / exec / D2H. Use buffers pinados (`cudaMallocHost`).
* **Medição:** `cudaEventRecord` para tempo; Nsight para timeline e identificação de bottlenecks.
* **Dica prática:** teste chunk size e número de streams (4–8 geralmente bons pontos de partida).

# Aula 18 — Síncrono vs Assíncrono, Profiling e Memória Pinned

## Principais ideias (resumo rápido)

* **Síncrono**: `cudaMemcpy` e `cudaDeviceSynchronize` bloqueiam e impedem overlap — CPU e GPU ficam esperando uma à outra → baixa utilização do sistema.
* **Assíncrono**: `cudaMemcpyAsync` + `kernel<<<...,...,0,stream>>>` em múltiplas *streams* permite sobreposição de cópias (H2D/D2H) com execução de kernels, quando *host buffers* são *pinned* (page-locked).
* **Pinned memory** (`cudaMallocHost`) é ESSENCIAL para que `cudaMemcpyAsync` seja realmente assíncrono — caso contrário o driver faz cópia intermediária e bloqueia.
* **Profiling**: `nsys profile` (Nsight Systems) revela timeline (transferências / kernels / sincronizações) e ajuda a medir speedup. Use `nsys-ui` para visualizar.

---

# Plano de otimização (passo-a-passo, direto ao ponto)

1. **Alocar host buffers pinned**:

   ```cpp
   cudaMallocHost(&h_imagem, bytes_total);
   cudaMallocHost(&h_saida,  bytes_total);
   ```
2. **Dividir dados em chunks** (linhas/tiles) e preparar `NSTREAMS` streams.
3. **Para cada chunk**: fazer `cudaMemcpyAsync(H2D, stream)`, lançar kernel no *mesmo* stream, depois `cudaMemcpyAsync(D2H, stream)`.
4. **Reusar buffers device** (alocar `d_blocos[i]` uma vez; não `cudaMalloc` dentro do loop).
5. **Medir com `cudaEventRecord`** (start/stop total e por-stream).
6. **Evitar `cudaDeviceSynchronize` no fluxo** — usar `cudaStreamSynchronize` por stream no final, ou `cudaDeviceSynchronize` só para validar/medir.
7. **Profile**: `nsys profile -o rel_assincrono --stats=true --trace=cuda,osrt ./assincrono`.
8. **Atenção ao uso de pinned**: não abuse — use para buffers de I/O. Liberar com `cudaFreeHost`.

# Código otimizado pronto (assincrono + pinned + reuse buffers)

Salva como `assincrono_pinned.cu` e compile com `nvcc -O3 assincrono_pinned.cu -o assincrono_pinned`.

```cpp
// assincrono_pinned.cu
#include <iostream>
#include <cuda_runtime.h>
#include <cstdlib>
#include <ctime>
#include <iomanip>

#define NSTREAMS 4   // experimente 2,4,6,8
#define LARGURA 3840
#define ALTURA  2160

__global__ void inverter_pixels(unsigned char *imagem, int tamanho) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < tamanho) imagem[idx] = 255 - imagem[idx];
}

float medir_tempo(cudaEvent_t a, cudaEvent_t b) {
    float ms=0; cudaEventElapsedTime(&ms,a,b); return ms;
}

int main() {
    std::srand((unsigned)std::time(nullptr));
    const int largura = LARGURA, altura = ALTURA;
    const int tamanho_total = largura * altura;
    const size_t bytes_total = size_t(tamanho_total) * sizeof(unsigned char);

    std::cout << "Imagem sintética 4K: " << largura << "x" << altura
              << " (" << (bytes_total/(1024.0*1024.0)) << " MB)\n";

    // ---------- pinned host buffers ----------
    unsigned char *h_imagem = nullptr, *h_saida = nullptr;
    cudaMallocHost(&h_imagem, bytes_total);
    cudaMallocHost(&h_saida,  bytes_total);

    for (int i = 0; i < tamanho_total; ++i) h_imagem[i] = (unsigned char)(std::rand()%256);

    // ---------- device buffers (one per stream) ----------
    const int linhas_por_stream = altura / NSTREAMS;
    const int pixels_por_stream = linhas_por_stream * largura;
    const size_t bytes_por_stream = size_t(pixels_por_stream) * sizeof(unsigned char);

    unsigned char* d_blocos[NSTREAMS];
    cudaStream_t streams[NSTREAMS];
    for (int i=0;i<NSTREAMS;i++) {
        cudaMalloc(&d_blocos[i], bytes_por_stream);
        cudaStreamCreate(&streams[i]);
    }

    // ---------- events ----------
    cudaEvent_t start_total, stop_total;
    cudaEventCreate(&start_total); cudaEventCreate(&stop_total);
    cudaEventRecord(start_total, 0);

    cudaEvent_t start_stream[NSTREAMS], stop_stream[NSTREAMS];
    for (int i=0;i<NSTREAMS;i++) {
        cudaEventCreate(&start_stream[i]);
        cudaEventCreate(&stop_stream[i]);
    }

    // ---------- pipeline: H2D async, kernel, D2H async ----------
    int threads = 256;
    for (int i=0;i<NSTREAMS;i++) {
        unsigned char *h_chunk_in  = h_imagem + i * pixels_por_stream;
        unsigned char *h_chunk_out = h_saida  + i * pixels_por_stream;

        cudaEventRecord(start_stream[i], streams[i]);

        // H2D async (pinned buffer enables real async DMA)
        cudaMemcpyAsync(d_blocos[i], h_chunk_in, bytes_por_stream,
                        cudaMemcpyHostToDevice, streams[i]);

        // kernel on same stream
        int blocks = (pixels_por_stream + threads - 1) / threads;
        inverter_pixels<<<blocks, threads, 0, streams[i]>>>(d_blocos[i], pixels_por_stream);

        // D2H async
        cudaMemcpyAsync(h_chunk_out, d_blocos[i], bytes_por_stream,
                        cudaMemcpyDeviceToHost, streams[i]);

        cudaEventRecord(stop_stream[i], streams[i]);
    }

    // sync and measure
    for (int i=0;i<NSTREAMS;i++) cudaStreamSynchronize(streams[i]);
    cudaEventRecord(stop_total, 0);
    cudaEventSynchronize(stop_total);

    float tempo_total = medir_tempo(start_total, stop_total);
    std::cout << "Tempo total (assíncrono + pinned): " << tempo_total << " ms\n";
    for (int i=0;i<NSTREAMS;i++) {
        float ms = medir_tempo(start_stream[i], stop_stream[i]);
        std::cout << "  stream["<<i<<"] = " << ms << " ms\n";
    }

    // sample output check
    std::cout << "Amostra (0..9):\n";
    for (int i=0;i<10;i++) std::cout << (int)h_imagem[i] << " -> " << (int)h_saida[i] << "\n";

    // cleanup
    for (int i=0;i<NSTREAMS;i++){
        cudaFree(d_blocos[i]);
        cudaStreamDestroy(streams[i]);
        cudaEventDestroy(start_stream[i]);
        cudaEventDestroy(stop_stream[i]);
    }
    cudaFreeHost(h_imagem); cudaFreeHost(h_saida);
    cudaEventDestroy(start_total); cudaEventDestroy(stop_total);
    return 0;
}
```

## Perguntas de prova que você deve saber responder (Aula 19)

## Perguntas — Respostas rápidas

1. Por que `cudaMemcpyAsync` pode não ser assíncrono se o host buffer não for pinned?  
    - Se o buffer do host for pageable, o driver aloca um buffer temporário page‑locked, copia os dados do host para esse buffer (cópia de CPU) e então inicia a DMA para o device. Esse estágio de cópia host→temp é síncrono, portanto `cudaMemcpyAsync` pode bloquear até essa cópia terminar, perdendo o overlap desejado. Somente buffers page‑locked/pinned permitem DMA direto e verdadeira assíncronia.

2. O que é uma *stream* CUDA e qual a relação entre streams e copy engines?  
    - Stream = fila ordenada de operações CUDA (memcpy async, lançamentos de kernel, events). Operações na mesma stream executam sequencialmente; em streams diferentes podem executar concorrente, dependendo do hardware. Copy engines são unidades DMA do dispositivo que realizam H2D/D2H; o número e tipo de copy engines determina quantas transferências podem ocorrer em paralelo e com kernels. Streams concorrentes disputam esses engines.

3. Quais são as etapas para pipeline H2D → kernel → D2H usando streams?  
    - Alocar buffers host page‑locked (cudaMallocHost) e buffers device reutilizáveis.  
    - Criar N streams.  
    - Para cada chunk:  
      1) cudaMemcpyAsync(host→device, stream)  
      2) lançar kernel com o mesmo stream: kernel<<<...,0,stream>>>(...)  
      3) cudaMemcpyAsync(device→host, stream)  
    - Opcional: usar cudaEventRecord/cudaStreamSynchronize para medir/sincronizar. Testar tamanho de chunk e número de streams para maximizar overlap.

4. Quando manter um vetor `x` permanentemente na GPU ao invés de copiá-lo por chunks? Por quê?  
    - Quando `x` é lido por muitos kernels ou por muitos chunks (reutilização alta), cabe na memória do device e não muda com frequência. Manter `x` no device evita cópias repetidas pela PCIe, reduz latência e aumenta throughput — especialmente em algoritmos iterativos ou em múltiplos SpMV/Stencil que reutilizam o mesmo vetor.

5. Como usar `nsys` para encontrar que parte do tempo é gasto em cópia versus kernel? O que procurar na timeline?  
    - Perfil: `nsys profile -o arquivo --trace=cuda,osrt ./meuPrograma`. Abra o .nsys‑rep no Nsight Systems.  
    - Na timeline, identifique faixas "CUDA Memory Copy" (HtoD, DtoH) e "CUDA Kernel". Compare durações, sobreposição e sequenciamento.  
    - Procure: cópias longas que não se sobrepõem a kernels (serialize), engarrafamentos no copy engine, barras de kernel com gaps (waiting on memcpy) e resumo/estatísticas em "CUDA API/CUDA Kernel" para tempos totais. Esses elementos mostram quanto tempo é gasto em transferência vs execução e se há overlap efetivo.

### 💭 Perguntas teóricas que podem cair

1. **O que é a prova de trabalho (Proof of Work) e como ela se relaciona com o SHA-256?**  
    Prova de Trabalho é um mecanismo onde quem minera tenta encontrar um *nonce* tal que o hash do bloco satisfaça uma condição de dificuldade (ex.: tenha N zeros iniciais). SHA-256 é a função de hashing usada para gerar esse valor: é determinística, unidirecional e com efeito avalanche — fácil de verificar, caro de buscar por tentativa/exaustão.

2. **Explique a diferença entre paralelismo com OpenMP e distribuição com MPI.**  
    OpenMP cria threads que compartilham o mesmo espaço de memória (memória compartilhada), ideal para paralelo intra-nó; é pragmático e de granularidade fina. MPI usa processos que comunicam por mensagens (memória distribuída), adequado para múltiplos nós do cluster e escalabilidade entre máquinas; exige gerenciamento explícito de comunicação.

3. **Por que mineração é um problema de HPC?**  
    Porque envolve busca massiva e independente de nonces (trabalho embaraçosamente paralelo), exige alto throughput de cálculo (hashes/s), otimização de uso de CPU/GPU e memória, e beneficia-se de técnicas e ferramentas de alto desempenho para reduzir tempo total.

4. **Como medir speedup e eficiência de uma aplicação paralela?**  
    Speedup = T_seq / T_par (tempo sequencial sobre tempo paralelo). Eficiência = Speedup / p (p = número de threads/processos). Medir tempos de parede, isolar overheads (I/O, inicialização), fazer várias execuções e usar cenários de strong/weak scaling para análise.

5. **Quais tipos de gargalos são comuns em algoritmos de hashing?**  
    - CPU-bound: limite pelo throughput do núcleo (operações aritméticas/bitwise).  
    - Memória-bound: latência de acesso, cache misses, acesso não-coalescente (GPU).  
    - Sincronização/Contention: locks, atomics, barreiras que impedem paralelismo ideal.  
    - Em GPU: divergência de warps e transferência Host↔Device (PCIe).

6. **Por que a passagem de objetos grandes por referência melhora o desempenho?**  
    Evita cópias de memória (custo de CPU e alocação), reduz uso de cache e largura de banda, melhora latência. Use referências const quando for leitura; cuide de concorrência e tempo de vida do objeto (ou mova quando for apropriado).

7. **Qual a diferença entre paralelismo em memória compartilhada e distribuída?**  
    - Memória compartilhada: threads/processos no mesmo nó acessam um único espaço de endereçamento; comunicação implícita via variáveis; requer sincronização (mutex, atomics).  
    - Memória distribuída: cada processo tem sua própria memória local; comunicação explícita por mensagens (MPI); melhor escalabilidade inter-nós, mas maior custo de comunicação e complexidade de partição de dados.

### 💭 Perguntas teóricas que podem cair — Respostas

1. **Explique o modelo de programação CUDA (host x device).**  
    Host = CPU: prepara dados, aloca memória, lança kernels e sincroniza. Device = GPU: executa kernels em paralelo, possui memória própria (global, shared, registers). Comunicação host↔device é explícita por cópias (a menos que se use memória unificada).

2. **Qual a diferença entre execução síncrona e assíncrona em GPU?**  
    Síncrona: a chamada bloqueia o host até a operação terminar (ex.: cudaDeviceSynchronize, cópias síncronas).  
    Assíncrona: operações são enfileiradas em streams e retornam imediatamente; host continua e precisa de sincronização explícita para garantir completude.

3. **Por que é importante minimizar cópias entre CPU e GPU?**  
    Transferências via PCIe/NVLink têm alta latência e largura de banda limitada; muitas cópias degradam throughput e tornam a GPU ociosa, reduzindo ganhos de paralelismo.

4. **Qual o papel da memória compartilhada no desempenho do kernel?**  
    Shared memory = SRAM de baixa latência por bloco. Serve como cache/manual tile para reduzir acessos à memória global, aumentar reutilização de dados e diminuir latência — quando bem usada, melhora muito o desempenho. Atenção a conflitos de bancos (bank conflicts).

5. **Como definir o número ideal de blocos e threads em uma GPU?**  
    - Threads por bloco: múltiplos de 32 (warp); valores típicos 128–1024 dependendo do kernel.  
    - Blocos: suficientes para manter todos os SMs ocupados (>> número de SMs).  
    - Balancear occupancy com uso de registros e shared memory; usar CUDA Occupancy Calculator e profiling para ajuste fino.

6. **O que é throughput e como ele é medido em um minerador?**  
    Throughput = quantidade de hashes computados por unidade de tempo (hashes/s). Mede-se contando hashes válidos/testados em um intervalo (ou via contadores de kernel) e dividindo pelo tempo de execução (pode ser kernel-only ou end-to-end).

7. **Quais são as vantagens e limitações de usar memória unificada?**  
    Vantagens: programação mais simples (menos cópias explícitas), coerência automática.  
    Limitações: possível overhead de page migration, latência imprevisível e menor controle de desempenho; em kernels de alto desempenho, cópias manuais e buffers pinados costumam ser mais rápidos.

8. **Explique o conceito de warp divergence e seu impacto no desempenho.**  
    Warp = grupo de 32 threads executado em SIMD/SIMT. Divergência ocorre quando threads do mesmo warp tomam caminhos condicionais distintos; o hardware serializa execuções diferentes, reduzindo utilização e throughput. Minimizar branches divergentes é crucial.

9. **Como streams podem ser usadas para sobrepor transferências e execução?**  
    Usando múltiplas streams com cudaMemcpyAsync e kernels assíncronos: enquanto uma stream executa kernel, outra pode transferir H2D/D2H de outro buffer (double buffering). Pinned host memory e separação de streams permitem sobreposição efetiva.

10. **Por que SHA-256 é adequado para mineração paralela?**  
    Cada tentativa de nonce é independente (embarrassingly parallel), sem dependências entre threads. SHA-256 é determinístico e de custo fixo, composto por operações bitwise e aritméticas que mapeiam bem a núcleos SIMD/SIMT, permitindo alto throughput quando distribuído em muitas threads.

# 🧩 Comparativo — Projeto 1 x Projeto 2

| Aspecto                      | Projeto 1 (CPU / OpenMP + MPI)     | Projeto 2 (GPU / CUDA)                      |
| ---------------------------- | ---------------------------------- | ------------------------------------------- |
| **Plataforma**               | Cluster Franky (CPU)               | Franky + Santos Dumont (GPU)                |
| **Linguagem**                | C++ com OpenMP/MPI                 | C++ com CUDA                                |
| **Paralelismo**              | Explícito (threads/processos)      | Massivo (milhares de threads)               |
| **Memória**                  | Compartilhada + distribuída        | Hierárquica (global/shared/registers)       |
| **Escalabilidade**           | Limitada por número de núcleos     | Limitada por largura de banda e memória GPU |
| **Métrica-chave**            | Speedup / Eficiência               | Throughput / Ocupação GPU                   |
| **Desafio**                  | Coordenação entre threads e nós    | Minimizar cópias e acesso não-coalescente   |
| **Ferramentas de profiling** | `time`, `htop`, `gprof`, MPI stats | `nvprof`, `nsys`, Nsight Compute            |
